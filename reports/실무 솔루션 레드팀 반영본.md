# 마케팅팀 데이터 얼라인: 진단과 실행 설계

> 이 문서는 **리더 혼자 보는 문서**입니다. 진단에 쓴 표현을 팀에 그대로 옮기지 마세요. 팀에는 6-(a)의 공지 1장만 보냅니다.

---

## 1. 한 줄 진단 (가설, 확신도 중)

> **가장 유력한 가설: 팀원들이 데이터를 싫어하는 것이 문제가 아닙니다. 리더의 목표가 '결정'으로 번역되지 않은 채 '작업'으로만 팀에 내려가고 있습니다.**

- 팀이 거부하는 것은 데이터가 아닙니다. **결과가 어떻게 나와도 아무것도 바뀌지 않는 노동**을 거부하는 것입니다.
  - Hubbard의 정보 가치 관점에서 보면, 결과에 따라 결정이 달라질 수 있었던 정보만 가치가 있습니다.
  - 실무자는 이걸 감으로 압니다.
- **번역 손실:** 리더 머릿속에서는 목표, 가설, 필요한 데이터, 판단 기준이 하나로 이어져 있습니다. 하지만 팀에 도착하는 건 마지막 줄인 "이거 정리해 주세요"뿐입니다.
- **디자인씽킹으로 다시 보면,** 지금의 데이터 체계는 사용자 리서치 없이 출시된 사내 서비스입니다. 사용자인 팀원과 무엇을 주고받을지가 아직 설계되지 않았습니다.
- **해법의 중심은 설득이 아닙니다.** 순서는 이렇습니다.
  1. 빼기
  2. 결정으로 번역하기
  3. 루프 닫기
  4. 기준 보여 주기
- 이 레버는 대부분 리더 손에 있습니다. 좋은 소식입니다.
- 다만 이건 아직 가설입니다. 아래 경쟁 가설과 함께 팀과의 대화로 걸러 내세요.

## 2. 근본 원인

### 증상별 원인 가설과 지금 확인할 수 있는 신호

| 증상 | 원인 가설 | 지금 확인할 신호 |
|---|---|---|
| "이거까지 해야 해?" | 목표가 '결정'과 '내가 움직일 수 있는 레버'로 번역되지 않았습니다. 그래서 리더 보고를 대신 써 주는 일처럼 느껴집니다. | "언제까지요?"는 묻는데 "이걸로 뭘 정하세요?"는 묻지 않습니다. |
| 회의 전날 몰아서 채움 | 일이 번거롭습니다. 콘솔 내용을 복사해 붙여야 하고, 매체마다 지표 정의가 다르고, 일은 늘기만 하고 빠지지는 않습니다. | 월요일 오전이 엑셀 정리 시간입니다. 같은 지표가 사람마다 다른 숫자로 나옵니다. |
| 해도 최소한만 함 | 루프가 닫히지 않습니다. 데이터 때문에 결정이 바뀌거나 유지된 장면을 본 적이 없습니다. | "지난달 데이터로 정해진 것 하나만 말해 볼래요?"에 아무도 답하지 못합니다. |
| 수준과 방향이 어긋남 | 기준이 리더 머릿속에만 있고, 결과물을 받은 뒤에야 드러납니다. | 피드백이 "좀 더 깊게"이고, 재작업이 2회 이상 반복되다가 결국 리더가 다시 씁니다. |
| 숫자만 나열하고 멈춤 | 해석에서 행동으로 넘어가는 과정을 본 적이 없습니다. 게다가 상사 앞에서 틀리는 것이 부담스럽습니다. | 보고서가 "추후 모니터링 필요"로 끝나고, 리더가 해석해 주기를 기다립니다. |
| 나쁜 숫자를 늦게, 포장해서 보고함 | 개인이 통제할 수 없는 ROAS나 매출로 추궁받는 구조입니다. 리더가 팀의 침묵을 동의로 읽고 있습니다. | "외부 요인" 해명이 잦고, 기간이나 필터를 바꿔 보고합니다. 반대 의견은 DM으로만 옵니다. |

### 경쟁 가설 (서로 배타적이지 않음)

| 경쟁 가설 | 확인 신호 | 맞다면 처방이 이렇게 달라짐 |
|---|---|---|
| 업무 용량 자체가 부족함 | 데이터 외 업무도 마감이 밀립니다. | 빼기 비중을 키우고 분석 기대치를 낮춥니다. |
| 역할과 맞지 않음 (콘텐츠·브랜드 담당에게 분석가 역할을 기대) | 특정 역할만 늘 관찰 단계에 머뭅니다. | 역할별로 기대치를 다르게 둡니다(4-4). |
| 결정권이 없음 (예산과 채널을 대표나 본부가 결정) | 데이터로 바꿀 수 있는 결정이 리더 손에 없습니다. | 윗선과의 정렬을 먼저 합니다. 결정권을 위임받거나 결정 목록에서 뺍니다. |
| 요청이 대부분 윗선에서 옴 | 감사표의 '처음 요청한 곳'이 위에 몰려 있습니다. | "보고용"이라고 표시하고, 자동화하고, 포맷을 협상합니다. |
| 리더의 기준이 결정에 필요한 수준보다 높음 | 재작업 사유가 결론이 아니라 형식, 깊이, 정밀도입니다. | 요청할 때 필요한 정확도를 적습니다. |
| 측정 설정이 깨져 있음 (UTM, GA4 이벤트) | 같은 지표가 사람마다 다른 숫자로 나옵니다. | 분석보다 측정 설정 정리를 먼저 합니다. |

### 리더 쪽 패턴 (탓이 아니라, 직관형 리더에게 구조적으로 생기는 번역 비용)

| 패턴 | 셀프 체크 |
|---|---|
| 가설은 말하지 않고 데이터만 요청한다 | 지난 8주의 요청 중 결정의 근거로 쓰인 것은 몇 %인가? |
| 기준이 결과물을 받은 뒤에야 드러난다 | '좋은 분석'의 기준을 지금 세 문장으로 쓸 수 있나? |
| 직관과 데이터가 부딪치면 설명 없이 직관을 택한다 | 팀이 "어차피 팀장님이 정하실 거잖아요"를 배우지 않았나? |
| 요청을 더하기만 한다 | 최근 데이터 업무를 늘리면서 뺀 일이 있나? |
| 위에서 받은 요청을 그대로 넘긴다 | 위에 "이것까지 해야 하나요?"라고 물어본 적이 있나? |
| 기준이 결정보다 연구자의 눈높이에 맞춰져 있다 | 최근 재작업 3건의 사유는 결론이 틀려서였나, 아니면 형식이나 깊이 때문이었나? |
| 시작은 빠르고 유지는 약하다 | 지난 1년간 도입했다가 흐지부지된 방식은 몇 개인가? 팀은 그걸 어떻게 기억하고 있나? |

> 마지막 패턴이 이 계획에서 가장 큰 실패 위험입니다. 그래서 아래 최소 버전(MVP)은 리더가 **주 2시간 안에 지킬 수 있는 크기**로 잘랐습니다.

## 3. 전문가들이 쓰는 방식

| 방식 | 출처 | 핵심 | 이 계획에서 쓰는 곳 |
|---|---|---|---|
| 결정 먼저 정하고 측정하기 | Hubbard, 『How to Measure Anything』(2007) / Basili & Weiss(1984)의 GQM | 측정의 가치는 결과에 따라 결정이 달라질 가능성에서 나온다. 목표, 질문, 지표 순서로 설계한다. | 요청할 때 붙이는 한 줄 |
| 통제할 수 있는 입력 지표와 주간 리뷰 | Bryar & Carr, 『Working Backwards』(2021) | 결과가 아니라 팀이 움직일 수 있는 입력을 관리하고, 매주 같은 형식으로 본다. | 개인은 입력 지표, 결과 지표는 팀 공동. 주간 리뷰로 기존 보고를 대체 |
| 의도 전달과 되짚기 | Bungay, 『The Art of Action』(2010) | 방법이 아니라 의도를 전하고, 받은 사람이 자기 말로 되짚게 한다. 정렬이 어긋났을 때 지시를 더 세세하게 하면 오히려 나빠진다. | 요청할 때 3분 동안 말로 되묻기 |
| 관찰, 의미, 행동 | Borton(1970), Rolfe 외(2001) / Minto의 결론 먼저 쓰기 | What, So what, Now what 순서로 쓴다. | 주간 3줄 |
| 예시로 기준 전달하기 | Sadler(1989) / 대조 사례 연구: Schwartz & Bransford(1998) | 기준은 문장보다 예시로 전달된다. 먼저 직접 해 본 뒤에 대조 사례를 보면 설명이 더 잘 들어온다. | 팀이 한 번 해 본 뒤 좋은 예와 약한 예를 보여 주기, 소리 내어 생각하기 |
| 작은 진전 만들기와 좌절 없애기 | Amabile & Kramer, 『The Progress Principle』(2011) | 의미 있는 일에서 느끼는 작은 진전이 가장 큰 일상 동기다. 좌절의 부정적 효과는 진전의 긍정적 효과보다 크다. | 48시간 안에 루프 닫기. 말없이 다시 쓰기, 데이터 무시하기 없애기 |
| 마찰 없애기 | Fogg, B=MAP(『Tiny Habits』) | 동기보다 쉽게 만드는 것과 기존 루틴에 붙인 신호가 행동을 만든다. | 먼저 빼기, 자동화, 기존 루틴에 얹지 말고 대체하기 |
| 학습 불안 낮추기 | Edmondson(1999) / Schein(Coutu, HBR 2002) | 변화의 이유는 정직하게 말하되, 위기감을 키우기보다 학습 불안을 낮춘다. | 리더가 틀린 가설을 먼저 공개하기, AI로 혼자 미리 검토받기 |
| 내면화 | Deci, Eghrari, Patrick & Leone(1994) | 재미없는 일도 근거를 대고, 귀찮음을 인정하고, 통제 대신 선택을 전하는 말을 쓰면 '내 일'로 받아들인다. | 한 문장으로 인정하기. 형식, 도구, 주기는 팀이 정하기 |

### 디자인씽킹 도구를 이 문제에 그대로 쓰기

- **직접 써 보기(도그푸딩).** 팀원의 주간 데이터 정리를 리더가 처음부터 끝까지 한 번 직접 해 봅니다. 옆에서 지켜보는 것보다 효과가 크고, 감시처럼 느껴질 위험도 없습니다.
- **소리 내어 생각하기(think-aloud)를 리더 자신에게.** 실제 데이터를 보면서 소리 내어 생각하는 20분을 녹화합니다. 직관형 리더가 무의식적으로 쓰는 판단 패턴이 그대로 교재가 됩니다.
- **극단 사용자.** 가장 저항하는 팀원이 가장 좋은 인사이트를 줍니다.
- **스폰서 편향.** 리더가 부하 직원을 인터뷰하는 건 제품 오너가 자기 제품의 사용성 테스트를 직접 진행하는 것과 같습니다. 오프닝 멘트 하나로는 직급 차이가 지워지지 않습니다.
  - 가능하면 제3자가 진행합니다.
  - 리더가 직접 한다면 '빼기'를 먼저 한 뒤에 짧게 합니다.
- **말보다 행동 신호.** "괜찮아요"라는 말보다 늦은 제출, 빈칸, 반복되는 "패스"를 믿으세요.
- **프로토타입.** 파일럿은 결정 1개, 사람 1~2명으로 합니다. 전원이 동시에 시작하면 프로토타입이 아니라 출시입니다.

## 4. 솔루션: 최소 버전(MVP)과 설계 원칙

### 4-1. 최소 버전(MVP): 이 5가지로 가치의 대부분을 얻습니다

| # | 할 일 | 팀이 느끼는 것 | 리더 비용 |
|---|---|---|---|
| 1 | **리더가 먼저 빼고, 권한을 줍니다.** 결정에 쓰이지 않은 내 요청 2개를 없애고, 윗선 보고 1건의 포맷을 협상합니다. 소액 예산을 옮기는 권한도 줍니다. | 일이 줄었다 | 1회 60분 |
| 2 | **요청을 한 줄로 번역합니다.** 정하려는 것, 내 짐작과 확신도, 대신 빼 줄 일을 씁니다. 이게 안 써지면 요청하지 않습니다. | 왜 하는지 알겠다 | 건당 3분 |
| 3 | **주간보고를 30분 리뷰와 3줄로 바꿉니다.** 3줄은 숫자, 그래서, 다음입니다. 정상 범위면 "패스"라고만 씁니다. | 쓸 게 줄었다 | 주 30분 |
| 4 | **48시간 안에 루프를 닫습니다.** "이걸로 ○○ 했어요", "유지했어요", "안 썼으니 다음부터 안 모아요" 중 하나로 답합니다. | 내 데이터가 쓰인다 | 건당 2분 |
| 5 | **기준을 한 번 꺼내 보입니다.** 팀이 한 번 해 본 뒤에 좋은 예와 약한 예 1쌍을 보여 주고, 리더가 소리 내어 생각하는 20분 녹화를 공유합니다. | 뭐가 잘한 건지 알겠다 | 격주 20분 |

**운영 규칙 (12주 동안)**
- 새로 생기는 루틴은 **2개 이하**입니다(요청 한 줄, 주간 3줄). 없어지는 것은 **3개 이상**이어야 합니다.
- 리더의 시간 예산은 **주 2시간 이내**입니다.
- 팀원 한 명이 데이터에 쓰는 총시간(모으기, 쓰기, 회의)은 **기준선보다 늘지 않아야 합니다.** 2주 차에 늘었다면 바로 범위를 줄입니다.
- 나머지는 6주 차 회고에서 **팀이 골라서 가져갈 때만** 꺼냅니다(5장 메뉴).

### 4-2. 리더가 팀에서 빼 줄 것

| 뺄 것 | 방법 | 시점 |
|---|---|---|
| 결정에 쓰이지 않은 리더 요청 | 최소 2개를 즉시 없앱니다. 이후에는 하나를 요청할 때마다 하나를 뺍니다. | 1주 차 |
| 승인 대기 | 주 예산 X원 이하의 재배분과 브랜드 가이드 안의 소재 교체는 먼저 하고 나중에 공유하게 합니다. | 1주 차 |
| 너무 잦은 수집 | 일간은 주간으로, 주간은 월간으로 바꿉니다. 콘텐츠와 브랜드는 격주에서 월간으로 봅니다. | 2주 차 감사 후 |
| 윗선 보고용 수작업 | "보고용"으로 표시하고 1순위로 자동화합니다. 포맷 협상은 리더가 합니다. | 2주 차부터 |
| 콘솔에서 시트로 복사하기 | 리뷰를 시작하기 **전에** 1건을 자동화하거나 AI 정리로 넘깁니다. | 3주 차 |
| 서술형 주간보고 | 3줄과 "패스"로 바꿉니다. | 3주 차 |
| 숨은 일 (UTM 시트, 지표 사전, 기록, 대시보드) | 기본은 리더, 툴, 대행사가 맡습니다. 팀원에게 맡길 때는 다른 일 하나를 빼 줍니다. 막내나 퍼포먼스 담당에게 자동으로 넘어가지 않게 합니다. | 상시 |

### 4-3. 이 계획에서 일부러 뺀 것 (팀이 원하면 나중에)

- 120분 워크숍, 포스트잇, 도트 투표, Fist-to-five
- 리더의 루브릭 채점, 사람에게 붙는 레벨, "전원 Lv2" 목표
- 익명 ADKAR 설문(작은 팀에서는 익명이 지켜지지 않습니다)
- 순환 반론자 역할(주니어에게는 벌칙이 됩니다)
- 정렬 테스트, 회신율이나 채움률 같은 준수율 지표
- **팀 앞에서 쓰지 않을 말:** ADKAR, GQM, North Star, 백브리핑, 골든 샘플, 루브릭, Lv1 기록자, HMW, AAR, ICE

### 4-4. 설계 원칙

- **리더가 정할 영역과 팀이 정할 영역을 먼저 선언합니다**(Tannenbaum & Schmidt, 1958).
  - 리더가 정하는 것: 분기 목적, 결정 목록, 실험 권한의 범위
  - 팀이 정하는 것: 볼 지표, 형식, 도구, 주기, 그만 모을 것
  - 끝까지 양보하지 못할 부분은 처음부터 리더 영역에 넣으세요. 답을 정해 놓고 "같이 정해요"라고 하면, 지시할 때보다 더 깊은 냉소가 생깁니다.
- **직관으로 정할 영역과 데이터로 정할 영역을 나눕니다.**
  - 직관과 정성 정보가 우선인 영역: 브랜드 톤, 크리에이티브 방향, 새 콘셉트
  - 데이터가 우선인 영역: 예산 배분, 채널 구성, CRM 발송 타이밍, 소재 중단
  - 리더의 짐작도 확신도와 함께 결정 로그에 적고, 분기마다 적중률을 공개합니다. 리더가 먼저 틀리는 장면이 가장 강한 안전 신호입니다.
- **결정권 지도를 만듭니다.** 결정마다 누가 정하는지(리더, 윗선, 팀원) 적습니다. 리더 권한 밖에 있는 결정은 위임을 요청하거나 목록에서 뺍니다.
- **평가와 분리한다는 건 말이 아니라 구조로 보여 줍니다.**
  - 리더 채점, 사람별 레벨, 준수율 지표를 두지 않습니다.
  - 이번 분기에는 평가에 반영하지 않습니다. 다음 분기부터는 결과가 아니라 참여 행동(3줄 작성, 지표 삭제 제안)만 반영한다고 지금 정해서 공개합니다.
  - 인사평가가 ROAS나 매출 기준이라면 "입력 지표만 책임지면 된다"는 말을 아무도 믿지 않습니다. 윗선과 조정이 안 된다면 그 사실을 솔직하게 말합니다.
- **팀원 개인에게 돌아가는 가치를 만듭니다.**
  - 데이터로 결정을 바꾸거나 지킨 사례는 본인의 커리어 자산입니다. 분기마다 1건을 본인 이름으로 정리해 포트폴리오에 쓰게 해 줍니다.
  - 기여자 이름을 공개할지는 1:1에서 본인 선호를 먼저 묻습니다. 정성 인사이트에도 기여자 이름을 붙입니다.

**역할별 기대치**

| 역할 | 데이터에서 하는 일 | 기대 수준 |
|---|---|---|
| 데이터 담당 (1명. 없으면 리더나 대행사) | 지표 정의, UTM, 자동화 | 정의와 측정 설정의 정확성. 이 사람의 다른 업무 20%를 공식적으로 빼 줍니다. |
| 해석 담당 (퍼포먼스, CRM) | 숫자를 해석하고 액션을 제안 | 기본은 해석, 제안은 도전 과제 |
| 맥락 담당 (콘텐츠, 브랜드) | 3줄과 현장 신호(댓글, DM, CS) | 플랫폼 기본 지표(저장, 공유, 프로필 방문, DM 문의)와 정성 맥락 |

### 4-5. 가정에 따라 달라지는 부분

| 상황 | 조정 |
|---|---|
| 3~4명 팀 | MVP만 합니다. 팀 세션은 60분, 주간 리뷰는 20분으로 하고 지표 트리와 설문은 하지 않습니다. |
| 6~8명 팀 | 담당자별로 가지를 나눈 지표 트리를 일찍 만듭니다. 리뷰에서는 예외만 다루고 정상 범위는 슬랙 이모지로 대신합니다. 익명 설문 2문항도 가능합니다. |
| PMF 이전 단계 | 트리 꼭대기에 North Star 대신 "이번 분기에 검증할 핵심 질문"을 둡니다. 효율보다 학습을 봅니다. |
| 예산과 채널 결정권이 윗선에 있음 | 윗선과의 정렬부터 합니다(4-2의 윗선 보고, 결정권 지도). |
| GA4와 UTM 설정이 부실함 | 분석보다 측정 설정 정리를 먼저 합니다. 손으로 셀 수 있는 지표로 시작합니다. |
| 외부 AI 사용이 제한됨 | AI 단계는 빼거나 사내에서 승인된 도구만 씁니다. |

## 5. 전체 로드맵 (12주): MVP 위에 팀이 골라서 더하는 방식

| 시점 | 리더가 할 일 | 팀이 느끼는 것 | 성공 신호 |
|---|---|---|---|
| **Week 0** (혼자 60분) | 지난 8주 요청을 점검합니다(결정에 쓰였나, 처음 요청한 곳은 어디인가). 없앨 내 요청 2개를 고릅니다. 의도 3줄(목적, 이번 분기 결정 3개, 하지 않을 것)을 씁니다. 실험 권한 금액, 직관과 데이터 영역, 결정권 지도 초안도 정합니다. | 없음 | 결정에 쓰이지 않은 내 요청을 2개 이상 찾음 |
| **Week 1** | 공지 1장을 보냅니다(6-a). 팀원 1명의 주간 데이터 정리를 직접 해 보고 1개를 더 없앱니다. 이때부터 요청은 한 줄 형식으로 합니다. | 보고 2~3개가 사라지고 권한이 생김. **새로 써야 할 문서는 0개** | 누군가 권한을 한 번 써 봄 |
| **Week 2** | 1:1을 20분씩 합니다(6-h). 들은 것 중 1개를 금요일까지 바꾸고 공지합니다. 윗선 보고 1건의 협상을 시작합니다. 60분 팀 세션을 엽니다. 순서는 감사표로 빼기, 근거가 있으면 더 잘할 수 있는 결정 3개 찾기, 3줄 형식 합의, 파일럿 결정 1개와 자원자 정하기입니다. | 내가 한 말 때문에 뭔가 바뀜 | 감사표에서 없애거나 줄인 항목 3개 이상 |
| **Week 3~6** (파일럿) | 수작업 1개를 먼저 자동화하거나 AI로 넘깁니다. 주간회의를 30분 리뷰와 3줄로 바꿉니다. 월간 1페이지는 파일럿 참여자(결정 1개, 자원자 1~2명, 리더)만 씁니다. | 주간 작성 시간이 줄어듦. 파일럿에 참여하지 않는 팀원은 '빼기'만 경험함 | 데이터가 근거로 쓰인 결정 2건 이상, 총시간이 기준선 이하 |
| **Week 4** | 팀이 한 번 써 본 3줄 옆에 좋은 예와 약한 예 1쌍을 놓고, 소리 내어 생각하는 20분 녹화를 공유합니다. 리더 약속 이행 여부를 익명으로 점검받습니다. | 뭐가 잘한 건지 보임 | 약속 이행률 80% 이상 |
| **Week 6** | 30분 회고(계속할 것, 바꿀 것, 그만할 것)를 합니다. 팀이 아래 메뉴에서 **다음 1개만** 고르고, 확대, 수정, 중단도 팀이 정합니다. | 다음 단계를 내가 고름 | 팀원이 먼저 개선안을 냄 |
| **Week 7~12** | 고른 메뉴를 한 번에 하나씩, 채널도 한 번에 하나씩 넓힙니다. 예시는 리더가 쓴 것 대신 팀원의 좋은 결과물로 바꿉니다. | | 월 4건 이상, 지표 수는 늘지 않음 |
| **Week 12** | 분기 회고에서 리더 직감의 적중률과 다음 분기 평가 정책을 공개합니다. 다음 분기 목표치는 팀원이 제안합니다. | | 리더가 말없이 고친 분석 0건 |

**메뉴: 팀이 원할 때만 고릅니다**

| 메뉴 | 이럴 때 고릅니다 | 비용 |
|---|---|---|
| 지표 트리 (North Star와 담당별 입력 지표 3~5개, 각각 가드레일 지표를 짝으로) | 6~8명이거나 담당별 가지가 필요할 때 | 리더 초안 1장과 비동기 코멘트 |
| 자동 대시보드 | 수작업이 월 2시간 넘는 항목이 있을 때 | 툴 비용과 셋업 시간(리더가 확보) |
| AI로 혼자 미리 검토받기 | 틀릴까 봐 제출이 늦어질 때 | 지침 1장(6-i) |
| 실험 백로그 (ICE 점수, 리더 아이디어도 같은 기준으로 심사) | 팀원 제안이 쌓일 때 | 격주 20분 |
| 수준 체크표 v0.2 | 해석이나 제안 단계 문서가 늘 때 | 30분 1회. 리더가 쓴 샘플만 함께 채점 |
| 데이터 다이어트 (쓰인 결정 수와 수집 비용으로 2x2 분류) | 지표가 다시 늘기 시작할 때 | 월 20분 |

**지표 트리를 고른다면 이렇게 잡으세요**
- **퍼포먼스:** GA4 기본 '참여 세션'을 씁니다. 10초 이상 머물거나, 핵심 이벤트가 있거나, 2페이지 이상 본 세션입니다. 체류 시간 기준을 따로 만들면 불필요한 셋업이 생깁니다.
- **콘텐츠와 SNS:** 플랫폼에서 바로 보이는 저장, 공유, 프로필 방문, DM 문의에 현장 신호를 더합니다. 제작 시간처럼 근태를 재는 듯한 가드레일은 두지 않습니다.
- **브랜드:** 월간 검색 수는 네이버 검색광고 키워드 도구에서 봅니다. 추세는 데이터랩으로 봅니다. 데이터랩은 조회 기간의 최댓값을 100으로 놓은 상대지수라서 기간을 바꾸면 스케일도 바뀝니다.
- **책임 구분:** 개인은 입력 지표만 맡고, North Star와 매출은 팀 공동으로 봅니다.

## 6. 바로 쓰는 도구 (복사해서 쓰세요)

### (a) 팀 공지 1장 (팀에 보내는 유일한 문서)

```
[데이터 업무, 이렇게 바꿉니다]

없어지는 것 (오늘부터)
- ___ : 제가 부탁드렸지만 실제 결정에 한 번도 쓰지 못했어요.
- ___ : 같은 이유예요.

줄어드는 것 (3주 차부터)
- 주간보고 → 각자 3줄 (숫자 / 그래서 / 다음). 별일 없으면 "패스".

새로 생기는 것 (하나)
- 제가 데이터를 부탁할 때 "무엇을 정하려는지 + 제 짐작"을 한 줄 붙입니다.

바로 쓰셔도 되는 것
- 주 예산 ___원 이하 재배분, 브랜드 가이드 안의 소재 교체는
  먼저 하시고 리뷰 때 공유만 해 주세요.

제가 지킬 약속
1. 부탁할 때마다 정하려는 것과 제 짐작을 먼저 씁니다.
2. 받은 결과에는 48시간 안에 "그래서 뭘 했는지" 답합니다.
   쓰지 않았다면 그 요청은 없앱니다.
3. 하나를 새로 부탁하면 하나를 뺍니다.

제가 어기면 바로 말해 주세요. 4주 뒤에 익명으로 점검받겠습니다.
```

### (b) 요청 한 줄 (리더가 씀)

```
[요청] 정하려는 것: ___ (결정일 __ / 결정하는 사람 __)
제 짐작: ___ (확신도 __%). 반대로 나오면 ___ 하겠습니다.
마감 __ / 대신 이번 주 빼 드릴 일: ___
(선택) 정확도: 방향만 / 비교 가능한 수준 / 외부 보고용
```
- 짐작과 "반대로 나오면"을 쓸 수 없다면 아직 요청할 단계가 아닙니다.
- 받은 사람이 **3분 동안 말로 되묻는 것**을 기본 절차로 둡니다. 따로 문서를 쓰지 않습니다.
- 윗선에서 급히 내려온 요청은 `[보고용]` 표시만 붙여서 처리합니다. 결정용인 것처럼 포장하지 않습니다.

### (c) 주간 3줄 (팀원이 씀)

```
[이번 주] 이름 / 담당
숫자: ___ (지난주 __ / 목표 __)      ← 정상 범위면 "패스"
그래서: ___ 때문인 것 같다 (확신 상·중·하)
다음: ___ 하겠다 (__까지) / 필요한 것: ___
(선택) 현장 신호: 댓글·DM·CS에서 본 것 한 줄
```

### (d) 주간 리뷰 30분 (기존 주간회의를 대체)

| 시간 | 내용 |
|---|---|
| 0~5분 | **리더가** 지난주 결정 로그를 공유합니다. 무엇을 했고 누구 데이터 덕분인지 말하며, 바꾼 것, 유지한 것, 중단한 것을 모두 셉니다. 첫 4주는 리더가 자기 쪽 나쁜 숫자나 틀린 짐작을 먼저 꺼냅니다. |
| 5~20분 | "패스"가 아닌 사람만 3분씩 이야기합니다. 결과 지표는 팀 공동으로만 봅니다. |
| 20~27분 | 바꿀 것, 유지할 것, 더 볼 것을 정합니다. 새 데이터 요청은 이 자리에서 한 줄 형식으로만 합니다. |
| 27~30분 | 그만 모을 것 1개, 리더가 치워 줄 장애물 1개를 정합니다. |

**규칙**
- 리더는 마지막에 말합니다.
- 결과 지표로 개인을 추궁하지 않습니다.
- 결정 로그는 리더가 씁니다.
- 리더가 빠지는 주에도 리뷰는 열립니다(미리 정한 1명이 진행).

### (e) 결정 로그 (리더가 씀)

| 날짜 | 결정 (바꿈/유지/중단) | 근거 링크 | 기여자 | (선택) 리더의 사전 짐작과 확신도, 맞았나? |
|---|---|---|---|---|

### (f) 데이터 부담 감사표

| 작업 | 담당 | 월 시간 | 연결된 결정 (없으면 "없음") | 처음 요청한 곳 (리더/윗선/외부) | 판정 |
|---|---|---|---|---|---|

**판정 기준**
- **없애기:** 결과가 어떻게 나와도 같은 결정을 했을 작업이거나, 해당 결정 주기 동안 한 번도 근거로 쓰이지 않은 작업입니다. 리더가 요청한 것이면 그 자리에서 없앱니다. 윗선이 요청한 것이면 리더가 협상합니다.
- **줄이기:** 빈도를 낮추고 지표를 3개 이하로 줄입니다.
- **자동화하기:** 결정에 쓰이고, 월 2시간 이상 걸리고, 소스를 연결할 수 있는 작업입니다.
- **지켜보기:** 예산 소진 속도, 추적 상태, 수신 거부율 같은 가드레일 지표입니다. 기준치를 벗어날 때만 알리고 평소에는 패스합니다.
- **유지하기(정성):** 댓글, DM, CS입니다. 형식만 통일하고 절대 없애지 않습니다.

**최소한의 측정 설정 규칙**
- 외부 링크는 값이 드롭다운으로 고정된 UTM 빌더 시트에서만 만듭니다.
- 캠페인명은 영문 소문자와 하이픈으로 씁니다. 한글은 인코딩 문제로 GA4에서 어긋납니다.
- 메타는 `{{campaign.name}}` 같은 동적 파라미터를 씁니다.
- GA4 핵심 이벤트는 3~5개로 둡니다.
- 데이터 보존 기간은 기본 2개월을 14개월로 바꿉니다. 탐색 분석에만 영향을 주고 표준 보고서와는 상관없습니다.
- 규칙 위반은 사람 문제가 아니라 시스템 문제로 다룹니다.

**자동화 순서 (툴과 예산에 따라 다름)**
1. GA4와 YouTube는 Looker Studio에 바로 연결합니다(무료).
2. 메타는 파트너 커넥터나 예약 리포트를 씁니다.
3. 네이버 검색광고처럼 API 접근이 어려운 매체는 반자동으로 처리합니다. 지정 폴더에 CSV를 넣으면 시트가 읽어 오는 방식입니다.

### (g) 월간 1페이지 (선택: 파일럿 참여자와 제안 단계에만)

```
[제목 = 결론]  예: "신규 소재 2종 중단, 첫 3초 재제작 A/B 제안"
연결된 결정: ___ / 작성자 / 기간
1. 결론 + 확신도(상·중·하)
2. 근거 숫자 3개: 이번 / 비교(전 기간·목표) / 출처
3. 다른 설명, 그리고 그걸 배제한 근거 (1~2줄)
4. 다음 액션: 담당 / 기한 / 판정 기준 / 중단 기준(가드레일)
5. 멈출 것 1개 / 리더에게 필요한 것(결정·예산·도움)
```

**수준 자가 체크** (작성자만 합니다. 리더는 채점하지 않습니다. 단계는 사람이 아니라 문서에 붙입니다.)

| | 관찰 | 해석 | 제안 |
|---|---|---|---|
| 목적 연결 | 요청받은 숫자를 정리함 | 연결된 결정을 적음 | 결과별로 할 일을 미리 적음 |
| 그래서 | "올랐다/떨어졌다" | 원인 가설과 근거를 적음 | 다른 설명을 배제하고 확신도를 적음 |
| 다음 | "추후 모니터링" | 구체적인 액션 1개 | 담당, 기한, 판정 기준, 중단 기준, 멈출 것까지 적음 |

**같은 데이터로 쓴 세 단계 예시**
- **관찰:** "10월 메타 CTR이 1.4%에서 0.9%로 떨어졌습니다."
- **해석:** "하락은 신규 소재 2종(CTR 0.6%)에서만 나타났고, 기존 소재는 1.4%를 유지했습니다. 3초 조회율도 신규 18%, 기존 31%여서 앞부분 후킹이 약하다는 가설을 뒷받침합니다. 두 소재 모두 노출이 2만 이상이고 학습 단계가 끝난 뒤의 데이터라서, 우연이나 학습 변동일 가능성은 낮습니다(확신도 중)."
- **제안:** "신규 2종을 멈추고, 기존 소재의 첫 3초 구조로 2종을 다시 만들어 11/1~14에 A/B 테스트하겠습니다. 3초 조회율이 25% 미만이거나 CPA가 기존보다 20% 이상 높으면 중단합니다. 예산은 재배분이라 추가 비용은 0원이고, 담당은 ○○입니다."

**해석할 때 자주 빠지는 함정 5가지**
1. 매체와 GA4의 어트리뷰션 기준 차이
2. 메타 학습 단계의 변동
3. 표본 부족
4. 계절성과 요일 효과
5. 상관관계를 인과관계로 읽기

**규칙**

### 혼자 보는 체크리스트

- [ ] **말없이 고치지 않는다.** 고칠 때는 이유 한 줄을 작성자에게 공유하고, 작성자 이름은 유지한다.
  - IKEA 효과 연구(Norton, Mochon & Ariely, 2012)에서 효과는 직접 만든 것을 완성하지 못했거나 해체했을 때 사라졌다.
  - 말없이 다시 쓰는 것도 같은 방식으로 주인 의식을 꺾는다고 추론할 수 있다.
- [ ] 질문할 때는 내 견해를 먼저 말하고 묻는다. 위계가 있는 조직에서 답을 숨긴 질문은 시험이 된다.
- [ ] 팀원이 "이 지표 필요 없어요"라고 하면 실제로 한 번 버린다.
- [ ] 직관에서 나온 새 아이디어는 탐색용 시간(업무의 10~20%)에 넣는다. 보는 지표는 분기 중에 바꾸지 않는다.
- [ ] 밤늦게 독촉하지 않고, 완료율로 순위를 매기지 않는다.
- [ ] 듣기만 하고 아무것도 바꾸지 않는 1:1은 하지 않는다. 묻지 않은 것보다 신뢰를 더 잃는다.
- [ ] 툴과 대시보드보다 질문과 리듬을 먼저 만든다.

### 계속 따라오지 않는 팀원이 있다면

1. **저항을 신호로 다룹니다.** 1:1에서 "이 데이터가 쓸모없는 이유"를 듣습니다. 맞는 말이면 공개적으로 없앱니다.
2. **못 하는 건지, 안 하는 건지 구분합니다.**
   - 시간이나 스킬이 문제라면 일을 빼 주거나 첫 1장을 리더와 함께 씁니다(숫자는 리더가, 해석은 본인이).
   - 의미를 못 느끼는 게 문제라면 그 사람의 레버와 연결된 결정 하나를 같이 고릅니다.
   - ADKAR를 1:1 관찰용으로 참고할 수는 있지만, 실증 근거가 제한적인 실무 프레임입니다.
3. **최소선은 주간 3줄 하나**로 리더 영역에 고정합니다. 나머지는 선택입니다.
4. **6주 뒤에도 하지 않는다면** 1:1에서 기대치를 문서로 분명히 하고, 평가에 반영되는 시점을 미리 알립니다. 공개적으로 지적하지 않습니다.
5. **역할 재배치를 검토합니다.** 예를 들어 맥락 담당으로 바꿀 수 있습니다.

## 9. Super KIKI 도전 질문
